# 0GDrive — Architecture Decisions

## Product
Private, encrypted personal file drive on 0G Storage: folders, upload/download, sharing, trash, versioning. Wallet-based identity, no backend accounts.

## Decisions

### D1 — Platform strategy: single web codebase, packaged
One **React + Vite** app (also deployable as a website/PWA), wrapped:
- **Mobile**: Capacitor (iOS/Android web view)
- **Desktop**: Electron first (native Node access → can use the SDK's `fs`-based paths and stream large downloads; Tauri can replace it later if bundle size matters)

Consequence: all 0G logic lives in a shared `core/` TypeScript package; the app shell stays thin. Browser-targeted code uses `@0gfoundation/0g-storage-ts-sdk/browser` + `vite-plugin-node-polyfills`.

### D2 — Encryption: encrypted by default
Every file is **encrypted client-side at upload**. Two modes:

- **Web shell (MetaMask)**: AES-256 with a per-account **drive master key** generated in-browser, stored in localStorage, with a mandatory backup download. Rationale (M1 amendment): ECIES *decryption* requires the raw secp256k1 private key, which injected wallets never expose — so ECIES-to-self is impossible in a MetaMask-only web app. The master key is the honest custody model there.
- **Node / desktop / any flow holding a raw key**: ECIES to the wallet pubkey (SDK v2 header) — decryption is pure key possession.

Sharing (M3) = re-wrapping per-file content keys to recipients' pubkeys. To make that possible, per-file keys (wrapped under the master key) will replace direct master-key encryption when the metadata layer lands.

### D3 — Metadata layer: encrypted manifest files (revised 2026-10-25; was 0G-KV)
Drive state lives in **small encrypted JSON manifests uploaded as regular 0G files**, tagged with an `0GDRIVE` domain tag:

- **Drive index manifest** (tag purpose `0x01`): the folder tree — source of truth for folder existence, names and nesting
- **Folder manifests** (tag purpose `0x02`, tag carries `keccak256(folder id)`): file records for one folder — a file operation re-uploads only that folder's manifest (one small tx)
- **Folder tree (2026-10-31; index v2):** the index holds `{ id, name, parent }` per folder instead of paths. A folder's id is permanent (`f:` + 16 random bytes) and is what its manifest is tagged with; paths are worked out from names and parents (`core/src/tree.ts`). So renaming or moving a folder is one index write however many files and subfolders it has, and a folder made later under a trashed folder's name gets a new id and starts empty (with path tags, the trashed folder's old listing came back). Drives from before (v1 index: a list of paths) need no copying: each existing folder's id **is** its old path, so its manifest keeps its tag; the index is rewritten as v2 on its next write. Trashed records keep `originalPath` (shown, updated to the folder's current path while it exists) and gain `originalFolder` (its id), so restore follows a renamed folder; records trashed before have only the path, which is the id of a pre-v2 folder. The root (`''`) and trash (`__trash__`) keep their path keys. The public `DriveStore` API still takes paths. App versions before v2 can't read a v2 index — fine before production.
- Discovery is fully serverless: scan `Submit` events by sender (verified on the public RPC: `sender` and the file root hash are indexed topics, `tags` ride in the event data), pick the highest-block manifest per tag, download, decrypt with the drive master key
- Trash = a reserved folder manifest (`__trash__`); deletes are metadata moves (blobs are immutable)
- File rename (2026-10-31): `DriveStore.renameFile` rewrites the folder's listing only (1 transaction; blobs carry no name). Refuses empty names, `/`, `.`/`..`, >255 characters and a name already in the folder ignoring case. The stored MIME type is kept (the dialog warns when the extension changes). With on-device AI on and loaded, the search entry's embedding is redone for the new name from the stored tags and excerpt (`renameEntry`); otherwise the old entry stays. Existing share links carry the old name. Folder rename: `DriveStore.renameFolder(path, newName)` (1 transaction via the folder tree; same name rules, refuses a sibling folder's name ignoring case); in the app (2026-10-31) a pencil on each sidebar folder row opens the same dialog as file rename (whole name pre-selected, live checks against sibling folders); the open folder and expanded tree rows follow to the new path. Test: `npm run test:folder-rename`.
- Moving files and folders (2026-10-31): a "Move to…" picker (folder tree, the current place and the moved folder's own subtree greyed out, "+ New folder in …" for a destination that doesn't exist yet) opened from a file's row, the selection bar, or a sidebar folder row. Folders: `DriveStore.moveFolder(path, toParent)` — one index write (changes `parent`), refuses a move into itself or below, and a same-named folder in the destination ignoring case; a new destination is created in the same write. Files: `moveRecords(…, { refuseNameClash: true })` — one `batchSubmit` transaction (index too if the destination is new), refusing a name already in the destination ignoring case (organize suggestions don't pass the option). Drag-and-drop is left for later; the picker also works on phones. Test: `npm run test:move`.
- Actions that change several listings (move to trash, folder to trash, restore, organize moves) write them all in **one** `batchSubmit` transaction (2026-10-30/31; `DriveStore.writeManifests`). The listing that must not lose a record (trash when trashing, the target folders when restoring or moving) is stored before the one that drops it, so a failure part-way leaves a duplicate, never a loss. Where `batchSubmit` is off: one transaction per listing, same order.
- Last-writer-wins on concurrent updates (v1); the DriveStore interface leaves room for a 0G-KV backend later

**Why the pivot from 0G-KV (D3 as originally decided):** research showed KV reads require a KV node — a self-hosted Rust service that only reconstructs streams listed in its own config; no public node exists on testnet (the docs' example endpoint is dead). Without one, KV needs a client-side replayer (decode + replay every batch + compaction) — strictly more machinery than manifest downloads, which reuse M1's proven upload/download path. KV's granular writes were the only advantage; per-folder manifests bound re-upload size adequately for v1.

**Note on "permanence":** 0G storage lifetime is ~1 year per fee payment (per the KV node design docs — renewal is done by re-writing). This applies to file blobs and manifests alike; a renewal/compaction pass is planned in M5.

**Unique names in a folder (2026-11-01).** Rename and Move refused a name already in the folder (ignoring case), but uploads and restores added a second file of the same name. Now names stay unique everywhere: before an upload, the app compares the dropped names with the folder, uploads still queued for it, and each other, and asks once: Replace (the old record moves to the trash in the same transaction, written before the folder listing so a failure leaves a record listed twice, never nowhere), upload under new names (one field per file, filled with "name (1).ext", numbered from the stem of a name already ending in " (n)"; checked like Rename, and against each other), Skip, or Cancel. Typing the new name was a user request: "Keep both" with a fixed "(1)" didn't let them choose it. `DriveStore.prepareFileRecords` enforces it too: a name taken meanwhile (another device) gets "(1)" rather than a duplicate. A restore into a taken name gets "(1)", reported in Activity. Test: `scripts/test-duplicate-names.mjs`; `npm run test:drive` covers the other-device case and Replace.

### D4 — Network: Galileo testnet (Turbo indexer) first
Chain 16602, `evmrpc-testnet.0g.ai`, `indexer-storage-testnet-turbo.0g.ai`, faucet at faucet.0g.ai. Config-switchable to mainnet/standard without code changes (starter-kit-style `config.ts`).

### D6 — Drive key management: hybrid recovery (Option C, 2026-10-26)
Replaces the M1 "generate key + download a backup file" UX. The drive master key `M` (random, per account) is wrapped under multiple keys and stored **on-chain as an encrypted backup manifest** (tag purpose `0x04`, public blob, encrypted content):

- **S** — derived from a fixed wallet signature (`0GDrive: drive key recovery v1` message, HKDF-SHA256): the primary recovery path. New device = connect wallet → one signature → full drive restored
- **P** — derived from a user-set password (PBKDF2-SHA256, 600k iterations, random salt): the wallet-loss fallback
- key-file export remains as the third path

Flow: new users get `M` created silently and are asked for **one signature** to enable recovery (two since D11: the message is signed twice as a determinism check); existing-drive detection offers restore before create (prevents two-drive conflicts). Verified E2E (`scripts/test-recovery.mjs`, 5/5: publish, signature restore, wrong-wallet rejection, password restore, wrong-password rejection; ~0.0015 0G per backup tx).

**Password recovery without the wallet (user decision, 2026-10-28).** As first built, the password restore sat behind "connect wallet", so it couldn't help in the case it exists for (a lost wallet; with the wallet, the signature already restores). Now the start screen offers "Open your drive with its recovery password": wallet address + password → the public backup is read, `M` unwrapped, and the drive opened **read-only** (a `VoidSigner` for the address; no upload / new folder / trash / organize / index controls; browse, preview, download and share work). The key stays in memory only (the device may not be the owner's); "export key file" is offered. Setting the password is a dialog (hidden input, typed twice, ≥12 characters, warning that the backup is public so the password must resist offline guessing, and that a new password replaces the old one); the sidebar shows "✓ recovery password · change" from the on-chain backup. Restores try the password as typed, then trimmed (it used to be set untrimmed but restored trimmed). Test: `npm run test:password`.

Security notes (recorded honestly): a leaked `M` (or `S`) means pre-leak content is **permanently** compromised — 0G ciphertext is public and immutable, so no rotation recalls it; rotation (`M′` + rewrap) only re-secures future data and is metadata-only (files never re-upload, since content is keyed by per-file `K_f` unchanged). `S` derivation assumes deterministic wallet signatures (stable in practice; password/file paths are the independent fallbacks).

Also fixed alongside: `DriveStore` now supports an incremental **event cache** (localStorage per address) — full rescans from block 0 were taking minutes at current chain heights.

### D5 — Finality: strict, bounded, self-repairing (2026-10-24, updated 2026-10-25)
`finalityRequired: true` by default: a successful upload return means every shard node in the covering set has sealed the sector. The original hang was traced to an **SDK bug** (fixed upstream in **1.2.13**): `splitTasks` sorted per-node task lists shortest-first while the dispatch loop's round count came from the first list — silently dropping the tail tasks of the node with more segments (our 1 MB file lost segment 4; node A could never seal; the SDK's finality wait — an unbounded `while(true)` over all selected nodes — hung forever). With 1.2.13 the same 1 MB strict upload completes and seals normally (verified 2026-10-25, cost 0.00127 0G).

`core` still enforces finality itself rather than trusting the SDK loop:
1. SDK upload always runs with `finalityRequired: false` (data-upload only)
2. `ensureFinality` polls the covering set every 5 s, up to `finalityTimeoutMs` (default 15 min)
3. If sealing stalls past 90 s, up to 2 **repair passes** re-upload with `skipTx: true` — no new fee; `splitTasks` skips finalized nodes and re-sends the unfinalized node's shard segments
4. On timeout: loud error telling the user to keep their local copy

Rationale for keeping the wrapper despite the upstream fix: the SDK's internal wait is still an unbounded loop with no timeout and no repair — any future segment loss (network flap, node rejection) reproduces the infinite hang. The wrapper is defense-in-depth with better failure semantics. Encryption is wrapped in `core` (not passed to the SDK) so the encrypted file instance is stable across upload and repair — ECIES uses a per-instance ephemeral key, and re-wrapping would produce a different root hash. Download location discovery falls back to the trusted node list when the indexer reports no locations. Caveat: the repair branch is implemented but not yet exercised in anger — it reuses the SDK's well-trodden `skipTx` path.

**Repair fix (2026-10-27):** every `skipTx` upload (repairs, batch segment uploads) now passes `skipIfFinalized: false`. The SDK's default skip check asks **one** node; for a small (1-segment) file, a node of the *other* shard holds none of it and reports `finalized: true` — so the SDK returned "already stored" and never sent the segment to the owning node. Before this fix, repair passes for small files could be silent no-ops. Found by the batch experiment (blob 0, 3 KB: shard-0 node FINAL with nothing to store, shard-1 owner `uploadedSegNum=0`).

### D7 — Batch submission: one wallet prompt per upload (2026-10-27)
The Flow contract's `batchSubmit(Submission[])` registers many blobs in one transaction (fee = sum of per-blob fees). `core/storage.ts → uploadBatch`:
1. Hash all files (`createSubmission`; roots folded from the submission nodes — no extra pass)
2. `finalize(roots)` hook: the caller builds the **folder manifest listing those files** and appends it to the same batch — possible because roots are known before signing
3. One `batchSubmit` → one wallet prompt; txSeqs read from the receipt's `Submit` events
4. Segments uploaded per blob with `skipTx` through a **no-transaction signer proxy** — a node that hasn't seen the log entry can never trigger a second, paid transaction
5. Strict finality per blob; the manifest's segments upload **only after every file sealed**. If a file fails, the manifest's log entry stays empty (readers fall back to the previous version) and the stored files are registered with a normal manifest write

Records written this way can't know their txSeqs (assigned at mining); `DriveStore` backfills `txSeqs`/`txHashes` from the wallet's `Submit` events on load. Enabled per network (`NetworkConfig.batchSubmit`). Galileo: verified with real uploads. Mainnet: on since 2026-10-31 (user decision: mainnet and testnet behave the same). Evidence so far: the mainnet Flow contract is a beacon proxy whose implementation has the same `batchSubmit` and `submit` selectors as Galileo's, and a simulated 3-blob `batchSubmit` (`eth_call` with a balance override, `scripts/check-batch-submit.mjs`, costs nothing) succeeds on both networks and returns consecutive txSeqs. Not yet run: a real mainnet upload through storage nodes and sealing (`NETWORK=mainnet node scripts/test-batch-submit.mjs`, needs a little real 0G); run it before production. The old per-file path remains for networks with the flag off.

Verified: `scripts/test-batch-submit.mjs` (raw protocol, 3 blobs → 3 `Submit` events, consecutive txSeqs, visible to the sender-topic history scan) and `scripts/test-batch-upload.mjs` (production path: 3 encrypted files + manifest stand-in, **1 transaction**, all sealed in 30 s, byte-identical, 0.0028 0G).

**Time to the wallet prompt (2026-10-31).** Every drive action used to make 10–12 sequential requests before the wallet was asked to sign (2.4–3.4 s from a well-connected server): event scan, a fresh download of the index and folder manifests the app had just loaded, the SDK's single-file checks (node status, does the file already exist on two nodes), and two price lookups. Now it is one batched JSON-RPC request (~0.25 s on testnet; ~0.75 s for the first, on a cold connection):
- **Manifest cache** (`DriveStore`): manifests by the root hash of their stored bytes — a root names one immutable upload, so an entry can't go stale; which version is current still comes from the event scan before every action. Seeded on load and on every successful write.
- **Single manifests take the batch path** (`uploadBatch` with one item) where `batchSubmit` is on, so no storage node is asked anything before the prompt.
- **Price fetched with the scan**: the action's `refreshEvents` fetches `pricePerSector` fresh, in the same request as the scan, and `uploadBatch` reuses it (≤ 30 s old). It is not cached for longer because the contract takes any fee (a simulated `batchSubmit` with no fee succeeds on both networks), so a stale price would silently under- or overpay rather than fail. The market's address is cached.
- **Incremental scan in one round trip**: `eth_blockNumber` and `eth_getLogs(from, 'latest')` together, on one shared provider per RPC URL with a static network (no `eth_chainId` calls) and ethers' 250 ms answer reuse off.

In the browser, ethers' `JsonRpcSigner` then asked the wallet for the block number and a gas estimate before sending (~0.9 s through the extension). Since 2026-10-31 `uploadBatch` sends `eth_sendTransaction` to a browser wallet directly, which estimates gas itself anyway: click → wallet request measured at 0.27–0.36 s (`scripts/time-wallet-prompt-browser.mjs`; 3.8–5.1 s before these changes). The wallet's own work before its popup comes on top. File uploads still hash (and encrypt) every file before the prompt: the transaction carries their roots.

**Hashing uploads ourselves (2026-11-01).** Measured in the browser (`scripts/time-upload-browser.mjs`), pick → wallet request was 1.1 s for 10 MB, 4.2 s for 50 MB and 15.8 s for 200 MB: ~12 MB/s, nearly all "preparing". The SDK hashes in pure JavaScript on hex strings (`@ethersproject/keccak256`, `hexConcat` per tree node, `splice` on a queue per pair), encrypts with pure-JS AES, on the main thread, one file after another, and after approval reads, encrypts and hashes each file again to rebuild the full tree for segment proofs, then reads and encrypts it a third time to send it. `core/src/merkle.ts` computes the same layout (flow padding, submission sub-trees, the segment tree with an odd last node carried up, proofs as the SDK's `proofAt`) on bytes, with WebAssembly keccak (`hash-wasm`) and WebCrypto AES-CTR, from **one** read: it keeps a 32-byte root per 256 KB segment, from which the submission, the root and every segment's proof follow. `uploadBatch` hashes items in 8 MB jobs (all items at once), which the web app spreads over up to 4 web workers (`web/src/hashPool.ts`), and sends segments itself (`zgs_uploadSegmentsByTxSeq` through the same relayed node list, one segment per request, 6 in flight) with the kept proofs. The encryption header is made by the SDK's `newSymmetricHeader`, and repair passes still go through the SDK's `skipTx` upload, given an `EncryptedFile` with the same header, so the bytes are the same. Equivalence: `scripts/test-merkle.mjs` (offline) compares roots, submissions, proofs, stored bytes and segment bytes with the SDK's across 23 sizes from 1 B to 33 MB, plain and encrypted; `uploadBatch` also checks the submission's folded root against the tree's before asking the wallet. Result: 0.5 s for 10 MB, 0.8 s for 50 MB, 2.1 s for 200 MB to the wallet (~16× on one thread in Node: 64 MB in 0.89 s vs 14.4 s), and 50 MB from approval to stored 27.2 s (was 35.6 s); a 40 MB file uploaded, sealed and downloaded byte-identical. A user then saw "preparing 8.3 s" for an 11 MB PDF once (0.2 s for the same file right after); it didn't reproduce on staging with smart search on and the model loaded (0.1–0.3 s, main thread never blocked). So when preparing takes ≥ 1 s, the Activity line now breaks it down: `files X s: starting workers …, reading … + hashing … across workers; listings …` (the first job's wait before it ran; reading — including encryption — and hashing summed over jobs; the manifests). `scripts/time-upload-browser.mjs` can now also time photos or text PDFs with smart search on (`SMART=1 KIND=jpg|pdf`) and reports main-thread blocking. The breakdown found it: on the user's laptop the first upload of a session spent "starting workers 1.8 s" (705 KB PDF) and "5.1 s" (40 MB pptx; reading + hashing 0.4 s + 0.4 s), the second ~0 — the workers were created on the first upload, while the search model was busy. Now (2026-11-01) the pool starts when the drive opens (`prestartHashWorkers`), each worker compiles the WebAssembly hasher on load, and files up to 8 MB are hashed on the page (milliseconds) instead of going to a worker at all. Test: `scripts/test-hash-workers.mjs`.

**Seeing where the time goes (2026-10-31).** The Activity line breaks the click → wallet-request time into steps (`core/timing.ts`: `chain` = the event scan with the batched price call, `listings` = manifest downloads not in the cache, `indexing` = an upload waiting for its search entries, `preparing` = hashing/encryption, `price` = waiting on the price beyond that; the rest is "other"), and says when the AI model download was running — a user saw 3.9 s → 2.8 s → 1.3 s on consecutive actions where the tests measure 0.3 s, and the steps tell network from contention. **Waking the wallet:** extension wallets run in a background worker the browser suspends after ~30 s idle, so the first request after a pause waits for it to start. Each action now sends the wallet a read-only `eth_blockNumber` as it starts (`wakeWallet`, in `refreshEvents` and `uploadBatch`), in parallel with the app's own ~0.3 s, which also warms the wallet's RPC connection for its gas estimate. Its effect is on the wallet's side of the wait, so it isn't in the logged number; judged by eye.

**Gas limit with a margin (2026-11-01).** The "setup stalls" in the browser tests (about 2 runs in 9) were batch transactions failing on chain: the wallet sent them with its bare gas estimate as the limit, and one used 517,473 of 525,066 gas (98.6 %, the 63/64 mark of an inner call running out) and reverted, gas spent. With a bare estimate, transactions used 92–99 % of it (the cost depends on chain state when mined). Real wallets may or may not add a margin, so users could hit it too. `uploadBatch` now estimates through the app's own warm RPC connection, adds 20 % (`GAS_MARGIN`), and sends that limit with the transaction (a browser wallet gets it as `gas`, so it doesn't estimate itself); if the estimate fails the wallet estimates as before. The margin isn't free on 0G: **the chain charges at least 80 % of the gas limit** (a 21,000-gas transfer sent with a 100,000 limit paid for 80,000; testnet and mainnet both at 4 gwei) — so 1.2 puts the charge floor at 0.96 × the estimate, about what transactions use anyway, rather than the 1.2 × a 50 % margin would cost. Activity shows the step as "gas estimate" when it takes ≥ 50 ms. `test-move` checks every transaction carried the app's limit, succeeded, and reported ≤ 90 % of it used.

**Keeping connections warm (2026-11-01).** With the breakdown in place, a user saw "chain check 2.0 s". Their `curl` to the RPC: connect 1.27 s, TLS done at 2.12 s, total 2.38 s — the request itself took **0.26 s**; ~2.1 s was opening a connection (slow DNS + TCP + TLS). Browsers and servers close idle connections, so an action after a pause paid that setup before its wallet prompt, and the wallet paid it again for its own gas/fee calls. Now (`web/src/keepWarm.ts`): the page preconnects to the RPC origin at load (`dns-prefetch` + `preconnect`, anonymous CORS), and while connected and visible it sends a read-only `eth_blockNumber` every 20 s to the RPC directly and through the wallet — keeping both connections open and an extension wallet's worker awake. Hidden tabs send nothing; becoming visible pings at once. Test: `npm run test:wallets` (pings while idle, none while hidden, one on return).

**Interrupted changes (2026-11-01).** A change's listings go on chain in one transaction and their data is sent only after it is mined (step 4 above). A user restored a file and closed the browser right after the transaction completed: no node ever got the listings. On the next open the drive fell back to the previous listings, so the file was still in the trash, and every load and action retried the empty ones (the Activity line showed "listings 18.6 s"). Probed on Galileo (`scripts/probe-unuploaded.mjs`): for such an entry, the nodes whose shard holds its segment report `finalized: false, uploadedSegNum: 0` indefinitely, the other shard's nodes report it finalized (they have nothing to store), and a download gave up only after ~7 s of retry rounds. Three changes:
1. **Finish it on the next visit.** `uploadBatch`'s `beforeSend` hands over every item's exact stored bytes (the encrypted listing) just before the wallet is asked; `DriveStore` keeps them on the device (`DriveDevice`; the web app uses IndexedDB, `web/src/driveDevice.ts`) and drops them once stored. If they're still there on the next load and their transaction is on chain, the change shows as done at once (the cache is seeded from them) and `resumeWrites` sends their segments to the existing log entries with `skipTx` through the no-transaction signer: no new prompt, no new fee. Stage order is kept: `then` items only after all `first` items. Saved changes whose transaction never appeared (rejected, or the page closed before sending) are dropped after 30 minutes. Only listing-only changes are saved this way; a file upload's own data isn't, so its manifest would point at missing files anyway.
2. **Ask before closing** while a write's transaction is sent but its data isn't on the nodes (`unstoredWrites()`, a `beforeunload` prompt).
3. **Give up fast, and remember.** After one pass over the nodes finds no segment, `downloadFile` asks the segment's holders (by shard) and throws `NotUploadedError` if every one that answers has no data; the drive skips that listing for 2 minutes (its upload may still be running elsewhere), and once its transaction is 30 minutes old marks it abandoned on the device for good and tells the user in Activity that the change was undone.
Tests: `scripts/test-interrupted-change.mjs` (browser: interrupted restore, close prompt, another browser sees it undone and gives up after one pass, this browser finishes it with no transaction) and `scripts/test-abandoned-listing.mjs` (Node, ~3 min, threshold shortened to 1 minute via `abandonedAfterMs`: undone but not abandoned before it, abandoned and told once after, skipped later).

### D8 — On-device AI, Phase 1: search & organize (2026-10-27)
All inference runs in the browser (transformers.js / ONNX Runtime WebAssembly, in a Web Worker); plaintext and queries never leave the device. Models download once from the Hugging Face CDN (ORT's wasm runtime from jsDelivr), with a fallback route through the app's server, and live in the browser cache.

| Job | Model | Size (q8) |
|---|---|---|
| Text embeddings (names, docs, queries) | `Xenova/paraphrase-multilingual-MiniLM-L12-v2` (384-d) | ~118 MB |
| Photo embeddings + zero-shot tags | `Xenova/clip-vit-base-patch32` (512-d) | ~90 MB vision + text |
| PDF text | pdf.js (first 2 pages) | — |

**Model choice was measured, not assumed:** `multilingual-e5-small` (the initial pick) and `-e5-base` both scored 6/10 on cross-language probes (e.g. "租房合同" vs an English lease) with ~0.01 mean margin; paraphrase-multilingual-MiniLM scored 10/10 with 0.36 mean margin at the same size as e5-small. CLIP is English-only, so photo **tags** (English words) also go into the photo's multilingual text embedding — "猫" reaches cat photos through the tag "cat". Camera-style names (`IMG_0042`, `PXL_…`, `Screenshot …`) are excluded from embeddings (they made all photos embed alike) but stay matchable by name.

**Storage:** a `SearchEntry` per file (int8-quantized vectors, tags, ≤280-char excerpt; ~1 KB) inside the encrypted folder manifest — no extra transactions. Built at upload in parallel with hashing; time-boxed (15 s) before the prompt so a first-run model download never delays an upload (late files get indexed via "Index older files").

**Features:** drive-wide search (any language; name, excerpt keyword, text and CLIP signals, best wins); "Index N older files" per folder (downloads, indexes locally, 1 transaction; replaced by background indexing, D15); organize suggestions (file vs folder topic centroids and folder-name embeddings; tuned for precision — winner must beat the runner-up and the current folder); moves via `DriveStore.moveRecords`: every touched manifest (each destination, the source, the index if a folder is new) in **one** `batchSubmit` transaction since 2026-10-30, destinations stored before the source so a failure leaves a duplicate listing, never a loss (one transaction per manifest where `batchSubmit` is off). Toggle in the sidebar ("On-device AI").

Calibration and regression: `scripts/test-search.mjs` (Node, real models: 19/19 queries, 4/4 suggestion checks on an English + Chinese corpus — small corpus, thresholds in `web/src/ai/searchcore.ts` may need retuning on real drives); `scripts/test-browser-ai.mjs` (headless Chromium: worker + model download + pdf.js, 7/7). Known limit: CLIP confuses receipts and invoices; no OCR (scanned PDFs are found by name/tags only).

Models warm up in the background as soon as a drive opens. An upload that starts during the one-time download waits only while the download looks close to done (estimated ≤90 s left, ≤3 min overall); otherwise the files go up unindexed and "Index older files" catches them later.

**Model download (~300 MB first visit; `web/src/ai/netfetch.ts`).** Six files dominate: MiniLM weights 118 MB + tokenizer 17 MB, CLIP vision 89 MB + text 65 MB + tokenizer 2 MB, ORT wasm 27 MB. transformers.js fetches all of them through `env.fetch`, which we replace with a wrapper that (1) counts bytes against a fixed plan of those files minus what Cache Storage already holds, so the search box shows one number that only goes up ("AI models 42% · 133 / 303 MB · 2.1 MB/s"); (2) resumes a download (HTTP Range) through the app's own server at `/_models/<host>/…` when no response arrives in 10 s, no bytes arrive for 15 s, or a large file crawls below 150 KB/s; (3) keeps the original CDN URLs as cache keys, so the route never causes a re-download. The route is a Vite dev/preview middleware (`vite.config.ts`, GET only, `huggingface.co` + `cdn.jsdelivr.net` only, follows the CDN's redirects); **a production deployment must provide the same route** — without it (detected by the missing `x-0gdrive-proxy` header) the browser just keeps the direct download. If loading fails, the search box shows "AI offline · retry" and search matches names. After a successful load the app calls `navigator.storage.persist()` so the browser doesn't evict the cache under disk pressure (Chrome grants it silently for engaged/installed sites, Firefox may prompt once; a refusal only means a possible re-download). Verified in headless Chromium with an empty cache: direct 25 s (~12 MB/s, no resumes); with both CDNs blackholed, switched to the server route and finished in 47 s; percent monotonic in both. Resume/stall/ignored-Range/no-route cases unit-tested against a mock CDN.

**Fitting phones: a trimmed text model on 0G Storage, one thread (2026-11-01).** In MetaMask's in-app browser smart search failed with "no available backend found. ERR: [wasm] RangeError: Out of memory" (the reason became visible with the error-reason change). Three changes:
1. **One ONNX Runtime thread, one hash worker on touch devices, one retry after out-of-memory.** The page isn't cross-origin isolated, so ORT can't run threads anyway; `numThreads = 1` asks for no threads. (It doesn't avoid the threaded memory reservation, as first believed: see the cap below.) Touch devices start one upload-hashing worker instead of up to four. An out-of-memory warm-up restarts the AI worker (dropping all it allocated) and tries once more.
2. **The text model trimmed to English and Chinese** (user decision: those two languages). paraphrase-multilingual-MiniLM-L12-v2's vocabulary (250,002 tokens, ~100 languages) is a 96 MB embedding table in the 118 MB q8 model, and a 17 MB tokenizer.json. `scripts/models/prune-text-model.py` keeps the 116,049 tokens made only of ASCII, Latin-1 letters (à–ÿ: café, José, Müller), Chinese characters and CJK / general punctuation. Text in those characters can only split into such tokens, so English and Chinese text gets the **same tokens and the same embeddings** as before (`scripts/models/check-pruned-model.mjs`: 11 texts incl. mixed, fullwidth, URLs, accents — cosine 1.000000; existing search entries stay valid). Other scripts (Japanese, Korean, Cyrillic, Latin Extended) lose their tokens. 3. **Hosted on 0G Storage** (user decision), unencrypted, one transaction (`scripts/models/upload-model-to-0g.mjs`; testnet tx 0xba39d058…cbf0, txSeqs 157341–157345), pinned in `web/src/ai/modelOn0g.ts` by root hash, txSeq, size and SHA-256. transformers.js asks for it under a made-up Hugging Face id (`0gdrive/minilm-en-zh`); `netfetch` serves those requests from 0G. The storage client needs Node polyfills workers don't get, so the AI worker asks the page (`fetch0g` message), which downloads through the node relay and hands the bytes over; the worker checks the SHA-256 before use (a mismatch is refused). Through the relay (HTTP/2) downloads now keep 24 in flight: 55 s → 19 s (direct to the nodes: 16 s); direct stays at 6; failures still halve the limit.

**The engine's memory reservation, capped (2026-11-02).** The out-of-memory came back on an iPhone (Chrome) after many refreshes in one tab; a new tab worked. The error is raised before any model loads: ONNX Runtime ships only threaded builds, and whatever `numThreads` says, its loader creates `new WebAssembly.Memory({ initial: 256, maximum: 65536, shared: true })`, room to grow to 4 GB. A shared memory can't move when it grows, so the browser reserves the whole maximum up front; an iPhone tab has little address space, reservations from earlier page loads aren't freed at once, and after some refreshes the 4 GB reservation fails (the one-thread change in item 1 above didn't avoid it). `web/src/ai/wasmMemory.ts` wraps `WebAssembly.Memory` in the AI worker (which runs nothing else) and caps a shared memory's maximum at **1 GB**; a smaller maximum is a valid import for the module. Measured (Chromium): 202 MB with the text model, 322 MB with the photo models too after indexing and searching. Nothing to redo when ONNX Runtime updates; the test fails if its loader stops asking for 4 GB or stops creating the memory this way. Verified: `npm run test:ai-memory` (dev server, or a deployment, whose built AI worker it starts directly), including on the dev server a simulated tab with room for 1 GB but not 4 GB, where the uncapped engine fails with the users' error and the capped one loads. Not tested in Safari's engine (it doesn't run on the test host).

### D11 — Wallets: a picker for installed wallets, and a signature check (user decision, 2026-10-30)
- **Picker (EIP-6963).** Installed extensions announce themselves; with more than one, Connect opens "Choose a wallet" (last used first, remembered per browser). With one, it connects directly. Wallets that don't announce still work through `window.ethereum`. The drive, the share-link page and the account/chain listeners all use the chosen wallet. No library and no third-party account.
- **Why recovery limits which wallets work.** The recovery key S and the sharing key are derived from the wallet's signature of a fixed message, so the wallet must give the *same* signature every time. Normal-key wallets do (RFC 6979: MetaMask, Rabby, OKX, Coinbase Wallet extension, Ledger/Trezor through them). Smart-contract and passkey accounts (Safe, Coinbase Smart Wallet) don't produce a plain signature by the address, and some MPC / social-login wallets sign with a random nonce.
- **Safety net.** Every recovery signature must recover to the account's address. At first setup (and when publishing the share key) the message is signed **twice** and the two must match: one extra prompt, once per drive. On failure nothing is published; the app explains and points to the key file. Test: `npm run test:wallets` (no funds needed).
- **Switching and staying connected (2026-10-31).** Any change of wallet or account — the wallet's `accountsChanged` with a different account, **Switch wallet or account**, **Disconnect** — reloads the page. Everything the app holds belongs to one account (drive, key, the recovery check that decides between "Create my drive" and restore, dialogs, uploads), and a fresh page is the one reset that can't leave any of it behind; before, a switch kept the previous account's recovery state, which could offer "Create my drive" to an account whose drive lives on another device. On load the app reconnects the last-used wallet with `eth_accounts` (never a prompt), only if it is already on the app's network. Switch asks the wallet with `wallet_requestPermissions` (its account chooser), falling back to `eth_requestAccounts`; Disconnect calls `wallet_revokePermissions` where supported and sets a per-browser flag so a reload stays disconnected until Connect. An action or upload in progress asks before a switch or disconnect drops it. Test: `npm run test:wallets`.
- **Not yet:** embedded / social-login wallets, which need a recovery design that doesn't depend on deterministic signatures. (WalletConnect: D13.)

After an upload's approval MetaMask opened it as a *new* tab: the connect screen there, while the user's own tab (which went on to finish the upload) sat behind it. Now no redirect: the user goes back with iOS's "◀ Chrome"/"◀ Safari" link or the app switcher (Android wallets usually return by themselves), as the "Approve in …, then come back here" bar says.
- **Fixes from the same report.** A wallet that approves another chain first (MetaMask does) and switches when asked used to leave Connect doing nothing: ethers fails every call on a provider once the chain has moved, so `connectWallet` now reads the account through a fresh one. The start screen shows "Reconnecting…" (at most 10 s) instead of a live button while the last wallet reconnects, "Connecting…" while connecting, and why a connect failed (it went only to the activity log, which the start screen doesn't show: the button looked dead). WalletConnect that doesn't start in 20 s is an error, not a wait. Not yet seen on a real phone: why a reload of the page there showed the start screen with a dead button (in Chromium, with a scripted wallet that behaves like MetaMask, a reload brings the drive back); the error now shown should tell.
- **Stuck saved data (2026-11-02, same iPhone).** Then on every load: "Reconnecting…", then a button that stayed at "Connecting…" with no "Approve in MetaMask" bar, so no request had reached the wallet: WalletConnect itself never produced a pairing link. An Incognito tab (nothing saved) connected fine, one tab only: the state WalletConnect saves in the browser (IndexedDB `WALLET_CONNECT_V2_INDEXED_DB`) was stuck. Now: no pairing link within 20 s is an error ("WalletConnect didn't start the connection"); the start screen offers **Start a new connection** after an error or 8 s of waiting, when WalletConnect was the last wallet; it clears that store (and older `wc@…` localStorage keys) and reloads. `?debug=wc` shows WalletConnect's log (and ours: start, saved session, relay, pairing, each request) on the page, as a phone has no console to read. Test: the relay's WebSocket held open but silent (Playwright `routeWebSocket`).
- **The cause: reads went to the wallet (2026-11-02, from that `?debug=wc` log).** It wasn't stuck data. After a reload the session restored fine, and then `eth_getBalance` went to MetaMask over the relay and never came back. The library sends every method the wallet *listed* to the wallet, `rpcMap` only covering the rest, and MetaMask lists reads too (`eth_getBalance`, `eth_call`, …). Just after pairing MetaMask is on screen and answers; after a reload it's in the background and answers nothing, so the reconnect hung, then every connect. Now every method except the wallet's own (`eth_sendTransaction`, `personal_sign`, `eth_signTypedData_v4`, `wallet_switchEthereumChain` / `wallet_addEthereumChain`) is a plain JSON-RPC call to our own RPC for the session's chain. ### D14 — PDF preview on phones: pages drawn with pdf.js (2026-11-02)
On an iPhone (Chrome) a PDF preview showed only its first page: the preview put the PDF in a frame, and in a frame every iPhone browser (all are Safari's engine) draws just page 1; Android Chrome has no PDF viewer in frames. Desktop browsers were fine.
- **Touch devices** (`pointer: coarse`, phones and tablets) get `web/src/PdfPages.tsx`: the pages stacked and scrollable, fitted to the width, drawn for the screen's pixel density (at most 3×, at most 4 MP per page), and a "Page 3 of 12" counter. **Desktop keeps the browser's viewer** (search, zoom, print).
- **Memory.** iPhones cap the memory of all canvases on a page, so a page is drawn only within one screen of the view and its canvas released when it leaves; placeholders keep each page's size (`aspect-ratio`) so nothing jumps.
- pdf.js is the copy smart search already loads for PDF text (`web/src/pdfjs.ts`, shared); it gets a copy of the bytes, because it hands its buffer to its worker and Download still needs them. A PDF it can't open says so (password-protected ones by name), with Download.
- Not in this version: pinch-zoom inside the preview, selectable text, links. Download opens the phone's full viewer.

Verified: `npm run test:pdf-preview` (fresh funded drive, 390 px touch at 3×, 10 checks: drawn not framed, page 1 sharp and fitted, only near pages drawn, end of a 12-page PDF drawn and page 1 released, counter, no sideways scroll, Download intact, a broken PDF, desktop still framed).

### D15 — Background indexing; search entries saved with the next approved change (user decision, 2026-11-02)
The user saw files without search entries and no "Index N older files" button: it counted only the open folder's files, and only in the drive view with smart search on. They asked for a background agent that finds and indexes such files unnoticed. Indexing can run unnoticed; saving can't: entries live in the encrypted folder listings, and every write is a transaction the wallet approves. Of three ways to soften that — ride along with approved changes, offer a quiet Save, or a funded in-browser session key that writes without prompts — the user chose the first two; the session key (changes how a drive's records are found, adds a key to look after) stays a later decision (Phase 2's spending key).
- **Indexer** (`SmartSearch.tsx`): while a drive is open, smart search is on, the models are loaded and nothing else runs (no upload, preview or change in progress), it takes the next file anywhere in the drive (not trash) with no entry, reads it like an upload would (same size limits; unreadable → name only), and indexes it on this device. A file that fails isn't retried until a reload. Read-only drives don't index. On phones this only runs when smart search was turned on there.
- **Kept on the device** (`searchPending.ts`): by file id, with the name and folder it was indexed under; encrypted (AES-GCM, key derived with HKDF from the drive key) in IndexedDB, per account. Search and organize suggestions use them at once. After each load, entries the drive now has, or whose file is gone or renamed, are dropped; moved files are followed.
- **Saved without a prompt of its own** (core `DriveStoreOpts.pendingSearch`): every folder listing written gets the pending entries of its files; listings of up to 20 other folders holding some are added to the same transaction (uploads too: after the files' records) as optional writes, so a failure there leaves them pending instead of failing the change. Costs a little more storage fee per change while entries are pending.
- **Save** in the sidebar ("N indexed on this device · Save") writes them all now, one transaction. The per-folder button is gone; the sidebar also shows "N files to index for search" and "N indexed by name only".

Verified: `npm run test:bg-index` (fresh funded drive, 12 checks: found in two folders and indexed with no transaction, searchable before saving, one upload's single transaction saves both folders' entries, present with the device store cleared, Save with one approval, name-only, 390 px).

## Verification (M3 core, 2026-10-26)
Sharing and streaming proven E2E on testnet (`scripts/test-share.mjs`, 11/11 checks):

- **Per-file keys**: every upload gets a random AES-256 file key, wrapped under the drive master key with AES-GCM (authenticated — wrong master key fails loudly). Owner reads via unwrap → decrypt ✓
- **Mode A — secret link**: file key rides in the URL fragment (`#s=`); recipient downloads + decrypts with **zero keys, no wallet** ✓
- **Mode B — wallet-gated link**: file key ECIES-wrapped (ephemeral keypair → ECDH → HKDF → AES-GCM) to the recipient's published pubkey; decrypts with their raw private key; wrong key rejected loudly ✓
- **Streaming**: `downloadFile(onPlainChunk)` decrypts per segment in place via the SDK's `cryptAt` (payload-relative CTR offsets, cross-fragment tracking) — streamed output byte-identical to buffered decrypt ✓
- **Public profiles**: unencrypted address→pubkey record as a tagged upload; discoverable via event scan ✓

Sharing model (user decision): Mode A universal (MetaMask recipients included); Mode B wallet-gated — same link plumbing, per-file-key architecture makes both a wrap of the same 32-byte key. Pre-M3 files (master-key-encrypted) cannot be link-shared. Creating a share writes nothing on-chain (user decision, 2026-10-28): the per-file share count that used to be recorded in the folder manifest cost a background tx + wallet prompt per link, and was dropped with the "Shared" column; old manifests' `shares` field is ignored.

**Mode B uses a derived sharing key (user decision, 2026-10-28).** Wrapping to the wallet's own public key meant the recipient had to paste their raw private key (injected wallets never reveal it). Now each account has a dedicated secp256k1 keypair derived with HKDF (`0gdrive/sharekey/v1`) from the same recovery signature that derives the recovery key S — independent outputs, so one can't be computed from the other. Its public key is published as `shareKey` in the backup manifest, so drive setup is still 1 signature + 1 tx. Opening a link: the recipient connects the addressed wallet (checked before signing), signs the recovery message (no tx), and the derived private key unwraps the file key; it's cached in localStorage next to the master key, so later links on that device need no prompt. Restoring a drive by signature or setting a password also caches/re-publishes it. Links carry `d: 1` and the public key they were wrapped to (`p`), so a mismatch reports "different sharing key" rather than a bare decrypt failure. Relies on deterministic signatures (RFC 6979), as recovery already does. Migration: accounts whose backup only has the legacy wallet `pubKey` see "update share key" (1 signature + 1 tx, keeps the password wrap); senders can still share to them, with a warning that the recipient needs their raw private key, and legacy links still open by pasting it. Fixed along the way: setting a recovery password re-published the backup without the share key.

Cost: ~0.0024 0G for the full test (file upload + profile publish).

## Verification (M2, 2026-10-25)
Full drive semantics proven on testnet: folder create, file records, implicit folders, trash (with `originalPath`), rename-with-file-move, empty-folder removal guard, and **restart recovery** — a fresh `DriveStore` with zero local state reconstructed the entire drive (folder list + all manifests + trash) purely from on-chain `Submit` events + downloads. 11/11 checks, ~11 metadata txs, 0.0137 0G total (~0.00125/tx).

Crucially, the first run of this test failed and led us down a diagnostic path whose initial conclusion was **wrong**: we believed testnet nodes were "losing" the root-hash index for small files. In fact (corrected 2026-10-25, after user review of the evidence): the `Submit` event's `identity` field simply **is not the file's data root for single-segment submissions** — the real root rides in `submission.nodes[0].root` — so `zgs_getFileInfo(identity)` never resolved for those files at any time. No data was ever lost; the nodes were healthy. The first test failed because `scanUploads()` treated `identity` as the root. The passing run works because the by-txSeq fallback (`submissionIndex` == txSeq → `zgs_getFileInfoByTxSeq` / `zgs_downloadSegmentByTxSeq`) sidesteps the unreliable field for all sizes. Also hardened: manifest candidates that decrypt to non-JSON (wrong drive key — AES-CTR never fails loudly) fall through to older versions instead of crashing.

**Root extraction fixed properly (2026-10-26):** the correct file root is computable from the `Submit` event alone by folding the submission's witness nodes right-to-left (`root = keccak256(node[i].root ‖ root)`, mirroring the node's `nodes_to_root` at log_entry_fetcher.rs:782; plain keccak over 64 concatenated bytes). This yields `tx.dataMerkleRoot` for all file sizes — verified across single-node small submissions and multi-node large ones. The event's `identity` topic equals this root only for multi-node (large) submissions and is a flow-derived hash otherwise; it must not be used as the file root. `scanUploads()` now extracts roots via the fold; the by-txSeq fallback (`submissionIndex` → `zgs_getFileInfoByTxSeq`) remains as insurance. Also confirmed: `storagescan-galileo.0g.ai/api/txs/{txSeq}` returns the correct root plus fee and a ~1-year expiration timestamp.
